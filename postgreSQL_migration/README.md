# Vastra Mahal rental backend: Aiven MySQL to Supabase PostgreSQL

This folder moves the rental-shop backend from the Aiven MySQL free tier to the Supabase free tier (PostgreSQL 17).

There are two ways to move the data:

- **Option A (automatic, recommended):** the app does it on its first start on Supabase. Hibernate creates the tables,
  then `MysqlImportRunner` copies every row from Aiven, and only then does the app start serving requests. You only
  set a few environment variables on Render and deploy.
- **Option B (manual):** run `migrate_data.py` from this folder on your own computer.

## What changed in the code

| File | Change |
| --- | --- |
| `pom.xml` | `mysql-connector-j` replaced by the PostgreSQL JDBC driver (`org.postgresql:postgresql`). |
| `application.properties` | Default `DB_URL` is now `jdbc:postgresql://...`, with a comment on which Supabase connection string to use. `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` keep their names. |
| `schema.sql` | Rewritten for PostgreSQL. The changes are listed below the table. |
| `entity/AuditLog.java`, `entity/RedundantTrailEntry.java` | `before_state` / `after_state` mapped as `jsonb` with `@JdbcTypeCode(SqlTypes.JSON)`. PostgreSQL refuses to store a plain text parameter in a JSON column, so without this every audit write would fail. |
| `migration/LegacySoftDeleteCleanupRunner.java` | MySQL-only `DELETE t FROM t LEFT JOIN ...` and `DATABASE()` replaced with `NOT EXISTS` and `current_schema()`. The old code would have failed, and logged a warning, on every start. |
| `repository/ItemRepository.java`, `service/ItemService.java`, `controller/ItemController.java` | Explained below the table. |
| `repository/CustomerRepository.java` | Customer list ordered by `lower(name)`. |
| `migration/MysqlImportRunner.java`, `migration/MysqlImportGateFilter.java` (new) | The one-time startup import (Option A). It does nothing unless `MYSQL_IMPORT_ENABLED=true`. |
| `pom.xml`, `application.properties` | `mysql-connector-j` kept (runtime only) for the import, and the `app.mysql-import.*` settings. |
| `.github/workflows/keep-alive.yml` | `mysql` ping replaced by `psql`, reading new `SUPABASE_DB_*` secrets. |
| Comments in `BookingService`, `RedundantTrailService`, `Dockerfile` | MySQL/Aiven wording updated. |

What changed in `schema.sql`:

- `AUTO_INCREMENT` became `GENERATED BY DEFAULT AS IDENTITY`.
- `JSON` became `JSONB`.
- MySQL's `ON UPDATE CURRENT_TIMESTAMP` was dropped (Hibernate's `@UpdateTimestamp` already maintains `updated_at`).
- Foreign key indexes were added, because PostgreSQL does not create them automatically.
- The incremental `ALTER TABLE` steps were folded into the `CREATE TABLE` statements.
- Every statement is now `IF NOT EXISTS`, so the file is safe to re-run.

Why the item repository changed: MySQL's default collation is case-insensitive and PostgreSQL's is not. Without a
fix, `dress-001` and `DRESS-001` would become two different items. Three things keep the shop's old behaviour:

- **Item codes:** look-up by code and the "code already in use" check use `IgnoreCase`.
- **Category filters:** the inventory and availability filters compare `lower(category)`.
- **Sorting:** lists are ordered by `lower(name)`.

Already portable, so unchanged: the booking overlap lock (JPA `@Lock`, `SELECT ... FOR UPDATE`), every JPQL query,
`CancelledBookingPurgeRunner`, and the `TIME` columns.

## Before you start

- **Supabase free tier:** 500 MB database, 2 active free projects per account, and a project is paused after
  7 days without activity. The daily keep-alive workflow prevents the pause.
- **Aiven must be running** (powered on) during the move. It is only read, never changed.
- **Option B only:** Python 3.9+ and Java 17+ on your computer (the Maven wrapper `./mvnw` is included).

## Steps

### 1. Create the Supabase project

1. In [supabase.com](https://supabase.com), create a new project. Pick the region closest to your Render service and
   save the database password.
2. Open **Connect** (top bar) and choose **Session pooler**. Copy the host (`aws-0-<region>.pooler.supabase.com`),
   the port (`5432`), the database (`postgres`) and the user (`postgres.<project-ref>`).

Two connection options do **not** work for this app:

- **Direct connection** (`db.<ref>.supabase.co`) is IPv6 only, and Render cannot reach IPv6.
- **Transaction pooler** (port `6543`) breaks prepared statements and the booking row lock.

The JDBC URL for the app is:

```
jdbc:postgresql://aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require
```

### 2. Back up MySQL

```bash
mysqldump -h <aiven-host> -P <port> -u avnadmin -p --ssl-mode=REQUIRED --single-transaction defaultdb > vastra-before-migration.sql
```

Do the move at a quiet time, when nobody is using the app. Phones that are offline queue their changes and replay
them later with their idempotency keys, so those are not lost.

### 3. (Optional) Run `schema.sql` in Supabase

Open the Supabase **SQL Editor**, paste all of [`../src/main/resources/schema.sql`](../src/main/resources/schema.sql)
and click Run. It adds the check constraints, `ON DELETE CASCADE` rules and foreign key indexes that Hibernate does
not create. Without it the app still works, because Hibernate creates every table and column. The file is safe to run
again later.

### 4. Move the data

#### Option A: automatic, on the first start (recommended)

1. **Render > Environment.** Set the new database:
   - `DB_URL` to the JDBC URL from step 1.
   - `DB_USERNAME` to `postgres.<project-ref>`.
   - `DB_PASSWORD` to the Supabase database password.

   And, for this one deploy, the old one (from the Aiven console, service overview):
   - `MYSQL_IMPORT_ENABLED` = `true`
   - `MYSQL_IMPORT_URL` = `jdbc:mysql://<aiven-host>:<aiven-port>/defaultdb?sslMode=REQUIRED`
   - `MYSQL_IMPORT_USER` = `avnadmin`
   - `MYSQL_IMPORT_PASSWORD` = the Aiven password
2. **Save and deploy.** On start the app:
   1. creates any missing tables in Supabase (Hibernate);
   2. connects to Aiven over TLS and reads one consistent snapshot;
   3. copies every table in one PostgreSQL transaction: items, customers and bookings first, then the accessories
      and payments that point at them. `TIME`, `JSON` (to `jsonb`) and booleans are converted; timestamps and enum
      text are copied unchanged;
   4. moves every id sequence past the highest copied id;
   5. compares the row count of every table and commits only if all match;
   6. records the import in a small table, `mysql_import_status`, so it never runs twice.

   While this runs, every request (the health check included) gets `503 Service Unavailable`, so Render keeps the
   old instance serving until the new one is ready. The startup clean-up jobs (`CancelledBookingPurgeRunner`,
   `LegacySoftDeleteCleanupRunner`) run after the import, on the imported data.
3. **Check the Render log.** You should see one `MYSQL_IMPORT_TABLE` line per table, then:

   ```
   MYSQL_IMPORT_DONE tables=9 rows=... ms=... Remove MYSQL_IMPORT_ENABLED and the other MYSQL_IMPORT_* settings.
   ```

   If anything fails (Aiven unreachable, wrong password, a count mismatch), the log shows `Application run failed`
   with the reason, nothing is saved in Supabase, and the app does not start. Render keeps the old instance running.
   Fix the setting and deploy again. A `MYSQL_IMPORT_TABLE_SKIPPED` or `MYSQL_IMPORT_COLUMN_SKIPPED` warning means
   something exists only in MySQL and was not copied. Stop and check before going on.
4. **Delete the four `MYSQL_IMPORT_*` variables** on Render. Leaving them is harmless (later starts log
   `MYSQL_IMPORT_SKIPPED`), but the Aiven password should not stay around.

Two messages you may see:

- **`These PostgreSQL tables already have rows: [...]`**: the Supabase database already has data, for example from an
  earlier test. Add `MYSQL_IMPORT_REPLACE_EXISTING` = `true`, deploy, and delete it again afterwards. It empties
  those tables before importing.
- **`MYSQL_IMPORT_LATE_WRITES table=...`**: the old instance, still on MySQL, saved something (a booking, a payment)
  in the few seconds the import took, and that row is not in Supabase. If nothing new has been saved on Supabase yet,
  run `delete from mysql_import_status;` in the Supabase SQL Editor, set `MYSQL_IMPORT_REPLACE_EXISTING` = `true`
  and deploy again. Otherwise re-enter the missing rows by hand.

#### Option B: manual, with `migrate_data.py`

1. Suspend the Render service (Render > service > Settings > Suspend), so no phone writes a booking during the copy.
2. Start the app once against Supabase, so Hibernate creates the tables:

   ```bash
   DB_URL='jdbc:postgresql://aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require' \
   DB_USERNAME='postgres.<project-ref>' DB_PASSWORD='<password>' \
   FCM_CREDENTIALS_BASE64=unused STORAGE_IMAGEKIT_PRIVATE_KEY=unused \
   ./mvnw spring-boot:run
   ```

   Wait for `Started VatsraMahalBackendApplication`, then press Ctrl+C.
3. Copy the data:

   ```bash
   cd postgreSQL_migration
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   cp migration.env.example .env       # fill in Aiven + Supabase values, download Aiven's ca.pem next to it
   python migrate_data.py --dry-run    # connects to both, shows the plan and row counts, changes nothing
   python migrate_data.py              # copies everything (add --truncate if it says tables already have rows)
   ```

   The script does the same as Option A (snapshot, one transaction, type conversion, order, sequences, count check)
   and must print `Done. All row counts match.` `sync_metadata` is reported as "only in PostgreSQL" if you ran
   `schema.sql`. That is expected, because the app never uses it. If the script prints `warn ... only in MySQL` for a
   column, stop and check, because that column's data would not be copied.
4. On Render, set `DB_URL`, `DB_USERNAME` and `DB_PASSWORD` as in Option A step 1 (without the `MYSQL_IMPORT_*`
   variables), deploy and resume the service.

### 5. Lock down Supabase's public API

Run [`supabase_hardening.sql`](supabase_hardening.sql) in the SQL Editor. Supabase otherwise exposes every table in
`public` (customers' names and phone numbers included) through its REST API to anyone holding the project's anon key.
The backend is not affected because it connects as the table owner. You can also turn the API off entirely in
Project Settings > Data API.

### 6. Check production and update GitHub

1. **Check:** `/actuator/health` returns `UP`. On a phone, open the inventory, a customer and a bill. Check the pickup
   and return times and the payments, then create and delete a test item.
2. **GitHub > Settings > Secrets and variables > Actions.** Add `SUPABASE_DB_HOST`, `SUPABASE_DB_PORT` (5432),
   `SUPABASE_DB_NAME` (`postgres`), `SUPABASE_DB_USERNAME` (`postgres.<project-ref>`) and `SUPABASE_DB_PASSWORD`.
   Delete the four `AIVEN_DB_*` secrets.
3. **Test the workflow:** run **Supabase PostgreSQL Keep-Alive** once by hand.

### 7. Retire Aiven

Keep the Aiven service (powered off is fine) for about a week, then delete it.

Afterwards you may delete `src/main/java/com/rentalshop/backend/migration/MysqlImport*.java`, the
`app.mysql-import.*` lines in `application.properties` and the `mysql-connector-j` dependency. Keeping them does no
harm.

## Rolling back

Until step 7 the old database is intact (the import only reads it). To go back, set the three `DB_*` variables on Render back to the Aiven
values and deploy the previous commit, which still has the MySQL driver. Bookings made on Supabase in the meantime
are not in MySQL.

## Tested

Before delivery, both options were run locally against MySQL 8.4 and PostgreSQL 17.

Option A (automatic import):

1. The original app ran on MySQL and created the data listed under Option B below.
2. The new app started on an empty PostgreSQL database (no `schema.sql`) with `MYSQL_IMPORT_*` set. It created the
   schema and imported 9 tables. Every value in every table was compared with MySQL and found identical, and all the
   checks listed under Option B passed.
3. A second start with the settings still present logged `MYSQL_IMPORT_SKIPPED`.
4. The same import into a database prepared with `schema.sql` also gave identical values.

Option B (`migrate_data.py`):

1. The original app ran on MySQL and created owners/devices, items, customers, a two-item bill with a jewellery
   accessory, a standalone booking, bill-level and booking-level payments, pickup and return with a withheld deposit,
   audit logs (JSON), and a redundant-trail row.
2. `schema.sql` was applied to PostgreSQL (twice, to prove it can be re-run) and the new app started on it.
3. `migrate_data.py` copied the data over TLS. Every value in every table was compared and found identical.
4. The new app then worked on the copied data:
   - pickup times shown exactly as entered;
   - a lowercase duplicate item code refused;
   - category filters and customer search ignoring case;
   - availability correct;
   - an overlapping booking refused (row lock);
   - new customers, bookings and payments got ids after the copied ones;
   - audit logs read and written as `jsonb`.
5. The legacy soft-delete cleanup removed only rows with no booking history and dropped the old column.

Unrelated to the database: the original app fails to start when `REDUNDANT_TRAIL_TELEGRAM_ENABLED=true`
(`TelegramBotApiSender: No default constructor found`). That bug exists before and after this migration.
